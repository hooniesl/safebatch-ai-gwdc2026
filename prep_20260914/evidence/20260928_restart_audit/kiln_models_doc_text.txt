Models
You find out which models you can call by asking the API. This page starts with that call, then keeps the per-model figures you need once you have picked an ID.
List the models you can call
One authenticated GET returns the models that are being served right now. That is the whole of what it answers: which IDs an inference request will accept today. It is not the full catalog — a model that is announced but not serving yet is not in it.

What to branch on
Of the four fields, one is worth reading in code:
data[].id
 — 
the value you put in the model field of a request. This is the field to branch on, and the set of IDs is what to compare between calls when you want to notice that the catalog changed.
object
, 
data[].object
,
owned_by
 — 
fixed strings ("list", "model", "bricksum"). They carry no routing or ownership meaning, so branching on them buys nothing.
data[].created
 — 
Unix seconds stamped when the gateway builds the response, not when the model was added. Every entry of one response carries the same value and the value moves between calls, so it cannot be used to detect a newly added model.
The list carries nothing else: no context length, no price, no capability flags. Those are in the reference table further down. For the full request and error contract of this endpoint, see
List models
.
Check a model before you send a request
There is no per-model lookup: a GET on /models/{model} is not served and answers a plain-text 404 rather than an error object. To ask whether an ID is servable, read the list and test for membership.

There are three reasons an ID is missing: the model is not served yet, it has been retired, or the ID is misspelled. The list is the only check that distinguishes them, so re-read it and pick an ID from what it returns rather than retrying the same string.
Model reference
Which source answers which question
GET /models
— 
answers “what can I call right now”. It returns only the models that are being served, so this is the list your code should trust. If a model is absent here, a request naming it is rejected, whatever any page says.
the model catalog
— 
answers “what do you offer, and at what price”. It carries every model with a status, including the ones that are not serving yet, plus the context length, pricing, capabilities, measured throughput and 90-day uptime that the API list does not return. The table below reads from it.
So the two do not compete. A model with a coming-soon status is in the catalog and not in the API list, and that is the expected state rather than a mistake. Take IDs from the API list and everything else from the catalog; where they disagree about whether a model can be called, follow the API list.

Max output tokens
 — 
not a per-model figure. The catalog publishes no separate output cap for any model, so set max_tokens per request, within that model's context length. Context length counts prompt and completion together, and a request that exceeds it is rejected with 400.
Data handling
 — 
Prompts and completions are processed to serve your request and to meter usage for billing. By default, your data is not used for training. Contact us if you need a data-processing agreement.

API surface
Streaming
: 
Supported
 (
stream=true
)
Reasoning effort
: 
reasoning_effort is passed to the model. gpt-oss-120b accepts low, medium and high; higher values trade latency for reasoning depth.
Request timeout
: 
The gateway ends a request after 60 minutes. A non-streaming request that sends no bytes for about 100 seconds can be cut at the network edge, so send long generations with stream: true.
